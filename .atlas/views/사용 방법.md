# View 작성 워크플로우

> **Last Updated**: 2026-02-06
> **Status**: Stable
> **Audience**: Dev / AI Assistant
> **Intent**: View 문서를 SSOT와 연동하여 작성하는 전체 흐름은 무엇인가?
> **Scope**:
> - In: View 초안 작성 → SSOT 연동 → RUN 작성 → 구현
> - Out: 개별 View/SSOT/RUN 작성 세부 규칙
> **Refs**: @RULE-SYS-002, @RULE-SYS-003, @RULE-SYS-004, @RULE-SYS-005

---

## Summary

View는 프로젝트 기능을 사람이 이해할 수 있는 수준으로 정리한 **비권위 문서**다. (@RULE-SYS-003#Rule-Statement)
세부 제약은 SSOT(@REQ/@RULE/@ADR)에 위임하고, View는 흐름과 연결만 담당한다. (@RULE-SYS-003#Rule-Statement)
변경 발생 시 SSOT를 먼저 업데이트하고, View/코드가 따라온다. (@RULE-SYS-002#Rule-Statement)

---

## Flow Map

```
[1. View 초안]     [2. SSOT 연동]     [3. RUN 작성]     [4. 구현]
     │                   │                  │              │
     ▼                   ▼                  ▼              ▼
  전체 기능을      규범 문장에          SSOT 참조하며     코드 작성,
  이해 수준으로    SSOT 앵커 추가       행동/검증/산출물   변경 시
  작성 (세부 제외)  (부족 시 SSOT 보강)  중심으로 작성     SSOT 먼저 반영
```

---

## Key Decisions

| 단계 | 결정 포인트 | 분기 |
|------|-------------|------|
| View 초안 | 세부사항 포함 여부 | 제외 → View / 포함 → SSOT로 이동 (@RULE-SYS-003) |
| SSOT 연동 | SSOT 존재 여부 | 존재 → 앵커 추가 / 부재 → SSOT 신규 작성 |
| SSOT 보강 | 보강 범위 | "검증 가능/불변 제약"만 허용 (@RULE-SYS-005#Rule-Statement) |
| RUN 작성 | 참조 대상 | SSOT 직접 참조, View만 참조 금지 (@RULE-SYS-004#Rule-Statement) |
| 구현 중 변경 | 변경 순서 | SSOT 먼저 → View/코드 따라옴 (@RULE-SYS-002#Rule-Statement) |

---

## Failure Modes

| 실패 유형 | 증상 | 해결 |
|-----------|------|------|
| View가 SSOT 복제 | 유지보수 지옥, 불일치 | 세부는 SSOT로 위임, View는 링크만 (@RULE-SYS-003) |
| SSOT 없이 규범 주장 | 검증 불가, 근거 없음 | Strong Claim에 앵커 필수 (@RULE-SYS-003#Violation) |
| RUN이 View만 참조 | 검증 기준 모호 | RUN은 SSOT 직접 참조 (@RULE-SYS-004#Rule-Statement) |
| 코드 먼저 변경 | SSOT와 불일치 | SSOT 먼저 업데이트 (@RULE-SYS-002#Rule-Statement) |
| SSOT에 설명 포함 | SSOT 비대화 | 검증 가능/불변 제약만 (@RULE-SYS-005#Violation) |
